# Model Decoration and Relations

How decaf model decoration is translated into Drizzle schemas by `@decaf-ts/for-drizzle`, and why the adapter takes the full-adapter path instead of extending Drizzle's decorators.

## The decoration-path decision

Drizzle ORM is **schema-first**: tables, columns, indexes and relations are declared by calling builder functions (`sqliteTable()`, `mysqlTable()`, `pgTable()`, `index()`, `foreignKey()`, …) and captured in plain schema objects. Drizzle has **no runtime class/property decorator layer comparable to TypeORM's `@Entity`/`@Column` decorators**, so there is no Drizzle-side decoration surface for decaf's `Decoration flavouredAs` API to extend into (the route `@decaf-ts/for-typeorm` takes).

`for-drizzle` therefore follows the **full adapter path** (the for-nano/for-couchdb style):

1. decaf's model decoration (`@table`, `@column`, `@pk`, `@index`, `@unique`, relation decorators, `@version`, `@timestamp`, `@generated`) remains the **single source of truth**;
2. `translateModel(model, dialect)` reads that decoration metadata at runtime and produces the dialect-specific Drizzle schema object (`sqliteTable`/`mysqlTable`/`pgTable` with columns, indexes, foreign keys and join tables) — the adapter generates and maintains the Drizzle schema for you;
3. validation is **not** delegated to Drizzle: Drizzle performs no model validation, so `@decaf-ts/decorator-validation` (`@required`, `@maxlength`, …) stays authoritative on the decaf side. Validation *constraints* are only *reflected* into the physical schema (`NOT NULL`, column length, `UNIQUE`).

Consequence: you decorate models exactly as you would for any other decaf adapter, and the physical schema follows.

## Declaring a model

```ts
import { BaseModel, Repository, pk, column, uses, index } from "@decaf-ts/core";
import { model, ModelArg, required, minlength, maxlength } from "@decaf-ts/decorator-validation";

@uses("drizzle")
@table("users")
@model()
class User extends BaseModel {
  @pk({ type: "String" })
  @column("user_id")
  id!: string;

  @required()
  @minlength(3)
  @maxlength(100)
  @index(["email"]) // composite index over (name, email)
  name!: string;

  @index()
  @column("email")
  email!: string;

  constructor(arg?: ModelArg<User>) {
    super(arg);
  }
}

const repo = Repository.forModel(User); // DrizzleRepository<User>
```

## What each decorator becomes

`translateModel(model, dialect)` reads the decoration metadata and produces a Drizzle table. The mapping (full table in the package [Description](../4-Description.md)):

| decaf decoration | Drizzle representation (SQLite / MySQL / PostgreSQL) |
| --- | --- |
| `@table("name")` / `@model()` | `sqliteTable("name")` / `mysqlTable("name")` / `pgTable("name")`; decaf's `??` framework prefix becomes `drizzle_` |
| `@column("col")` | the property is stored under the physical column name `col` |
| `@pk({ type })` | primary-key column; `autoincrement` added when the key is also `@generated` and numeric (PostgreSQL emits `GENERATED BY DEFAULT AS IDENTITY` in the DDL instead of inline autoincrement) |
| `@required()` | `.notNull()` |
| `@unique()` | `.unique()` |
| `@maxlength(n)` | `text({ length })` / `varchar({ length })` (capped at 65535) / `varchar({ length })` (capped at 10485760; unbounded `text` otherwise) |
| `@index(...)` / `@index(["other"])` | table-level `index()` extra + `CREATE INDEX` DDL via `adapter.index()` |
| `@version()` | integer column (optimistic-lock versioning, decaf-side) |
| `@timestamp()` | `integer({ mode: "timestamp_ms" })` / `datetime` / `timestamp` |
| `@generated()` (or a `@pk` with a sequence) | `integer().primaryKey({ autoIncrement: true })` / `int().primaryKey().autoincrement()` / `GENERATED BY DEFAULT AS IDENTITY` |

The adapter's decoration wiring also overrides `@date()` for the drizzle flavour with the SQL-safe `SQL_TIMESTAMP_FORMAT` (`yyyy-MM-dd HH:mm:ss`), because SQLite and MySQL `DATETIME` columns reject decaf's default timestamp format.

Property *types* map from the decorated design type:

| decaf type | SQLite | MySQL | PostgreSQL |
| --- | --- | --- | --- |
| `String` | `text` | `varchar` | `text` (`varchar(n)` with `@maxlength`) |
| `Number` | `integer` | `int` | `integer` |
| `BigInt` | `integer` | `bigint` | `bigint` |
| `Boolean` | `integer({ mode: "boolean" })` | `boolean` | `boolean` |
| `Date` | `integer({ mode: "timestamp_ms" })` | `datetime` | `timestamp` |
| object / other | `text` | `varchar` | `jsonb` |

Translated schemas are cached per `dialect:model`, so the same Drizzle table object is reused across calls (Drizzle table identity matters).

## Relations

Relations are declared with the standard decaf decorators and are materialised in the generated schema:

- **`@oneToOne` and `@manyToOne`** create a foreign key from the declaring model to the target's primary key. The relation property acts as the FK column; if it is not also a `@column`, an FK column is generated automatically. `Cascade` options map to `ON DELETE`/`ON UPDATE` actions (`Cascade.CASCADE` → `cascade`, otherwise `no action`).
- **`@manyToMany`** generates a join table named `<table>_<property>_join` with a composite primary key over `source_id`/`target_id` and foreign keys to both parent tables.
- **`@oneToMany`** is the inverse side: the foreign key lives on the owning `@manyToOne` side of the target model, and no extra column is emitted on this model.

```ts
import { BaseModel, pk, column, uses, oneToOne, oneToMany, manyToOne, manyToMany } from "@decaf-ts/core";
import { model } from "@decaf-ts/decorator-validation";
import { Cascade } from "@decaf-ts/db-decorators";

@uses("drizzle")
@table("profiles")
@model()
class Profile extends BaseModel {
  @pk({ type: "String" })
  id!: string;
  constructor(arg?: any) { super(arg); }
}

@uses("drizzle")
@table("posts")
@model()
class Post extends BaseModel {
  @pk({ type: "String" })
  id!: string;

  @manyToOne(() => User, { delete: Cascade.CASCADE, update: Cascade.CASCADE })
  author!: User;

  @manyToMany(() => Tag, { delete: Cascade.CASCADE })
  tags!: Tag[];
  constructor(arg?: any) { super(arg); }
}

@uses("drizzle")
@table("tags")
@model()
class Tag extends BaseModel {
  @pk({ type: "String" })
  id!: string;
  constructor(arg?: any) { super(arg); }
}

@uses("drizzle")
@table("users")
@model()
class User extends BaseModel {
  @pk({ type: "String" })
  id!: string;

  @column("name")
  name!: string;

  @oneToOne(() => Profile, { delete: Cascade.CASCADE })
  profile!: Profile;

  @oneToMany(() => Post)
  posts!: Post[];
  constructor(arg?: any) { super(arg); }
}
```

With this decoration, `adapter.index(User, Post, Tag, Profile)` emits `CREATE TABLE` statements for all four tables, the `posts.author` and `users.profile` foreign keys, and the `posts_tags_join` join table — plus any declared indexes.

## Materialising the schema

Two supported routes (detailed in [Migrations](./Migrations.md)):

- `await adapter.index(...models)` — translate and apply `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX` DDL immediately (the `??sequence` bookkeeping table used by decaf sequences is included automatically);
- `DrizzleMigrator.generate(...)` / `DrizzleMigrator.migrate(...)` — emit versioned SQL files and apply them through Drizzle's programmatic migrator.
